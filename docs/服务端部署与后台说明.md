# 服务端集中回收与研究者后台 · 部署说明

> 适用：把不同设备完成的实验记录汇聚到同一持久化存储，并提供受保护的研究者后台（查看 / 详情 / 导出 JSON+CSV）。
> 本文档区分「已实现」「需你手动配置/部署」「未验证」。未部署前，网页仍是纯本地模式。

---

## 一、架构与数据存放位置

- **存储**：Cloudflare **D1**（边缘 SQLite）。这是**真正的持久化数据库**，区别于仅有接口无存储的空壳；记录写入后跨请求、跨设备、跨时间保留。
- **代码位置**：`functions/_shared/app.mjs`（统一请求处理逻辑，被 Pages Functions 与独立 Worker 共用）、`store.mjs`（D1 / 内存两种后端）、`auth.mjs`（登录与 JWT）、`csv.mjs`（CSV 构建）、`admin-ui.mjs`（后台页面）。
- **数据存放**：D1 数据库（绑定名 `DB`）。**不**写入任何第三方服务、不收集 PII、不发送浏览器未提交的内容。
- **存放内容**：每条记录以 `participant_id` 为主键；完整原始 JSON 保存在 `raw_json` 列，后台 CSV/JSON 导出**直接从服务端记录生成**，与原始提交一致。

## 二、两种部署方式（任选其一）

### 方案 A（推荐）：Pages Functions，与实验页同域、无需 CORS
现有项目已是 Cloudflare Pages。把本仓库的 `functions/` 目录一起部署即可，`/api/*` 与 `/admin` 与实验页同域。

1. 创建 D1 数据库：
   ```
   wrangler d1 create ai_label_exp
   ```
   记下输出的 `database_id`。
2. 在项目根或 `wrangler.toml` 中绑定 D1（Pages 项目在 Cloudflare 控制台的 *Settings → Functions → D1 database bindings* 绑定，或本地 `wrangler.toml` 配置 `[[d1_databases]]`：`binding = "DB"`）。
3. 初始化表结构（执行 `deploy/schema.sql`）：
   ```
   wrangler d1 execute ai_label_exp --file=deploy/schema.sql
   ```
4. 设置密钥（**务必用 Secret，切勿明文写入代码**）：
   ```
   wrangler secret put ADMIN_PASSWORD   # 研究者后台密码
   wrangler secret put JWT_SECRET        # JWT 签名密钥（随机长字符串）
   # 可选：仅允许实验页来源提交，防滥用
   wrangler secret put ALLOWED_ORIGIN    # 例如 https://ai-label-verification-experiment.pages.dev
   ```
5. 重新部署 Pages（推送含 `functions/` 的提交，或在控制台触发部署）。
6. 在 `index.html` 顶部 `EXP_CONFIG.DATA_ENDPOINT` 填写 `https://<你的pages域名>/api/submit`。
7. 研究者后台：访问 `https://<你的pages域名>/admin`，用 `ADMIN_PASSWORD` 登录。

### 方案 B：独立 Worker（跨域，需要 CORS）
若不想改动 Pages Functions，可部署 `deploy/worker.mjs` 为独立 Worker（代码见 `deploy/wrangler.example.toml`）：

1. `wrangler d1 create ai_label_exp`，在 `wrangler.example.toml` 填入 `database_id`，改名 `wrangler.toml`。
2. 执行 `deploy/schema.sql` 初始化表。
3. `wrangler secret put ADMIN_PASSWORD` / `wrangler secret put JWT_SECRET`。
4. `wrangler deploy`。
5. 在 `index.html` 的 `EXP_CONFIG.DATA_ENDPOINT` 填写 `https://<worker子域>/api/submit`；后台访问 `https://<worker子域>/admin`。

> 跨域时 Worker 已在 `/api/submit` 返回 CORS 头（`Access-Control-Allow-Origin` 取 `ALLOWED_ORIGIN`，未配置则 `*`，仅用于匿名记录提交，不含任何身份信息）。

## 三、幂等与重试（不会重复建记录）

- 前端：完成提交后把 `participant_id` 与条件绑定在本机会话；服务端返回成功才标记 `server_synced`，避免对已同步会话重复提交。
- 服务端：以 `participant_id` 为主键 `INSERT ... ON CONFLICT DO UPDATE`。同一编号重试 → **不新增行、不重复计数**；`server_received_at` 保留首次接收时间，不随重试更新。
- 前端“同步失败”时：本机记录保留，完成页显示「重试同步」按钮；服务端拒绝（校验失败 / HTTP 非 2xx）时**前端不会提示成功**。

## 四、研究者后台（访问控制）

- **无硬编码密钥**：`ADMIN_PASSWORD` 与 `JWT_SECRET` 仅存在于 Cloudflare Secret；前端 `admin-ui.mjs` 不含任何密码或长期令牌。
- **登录流程**：后台页面输入密码 → `POST /api/admin/login` → 服务端常数时间比对密码 → 签发 HMAC-SHA256(JWT) 短时效（8h）令牌 → 令牌仅存于浏览器 `sessionStorage`（运行时，刷新即失效）。
- **受保护接口**：`/api/admin/records`、`/api/admin/record/:pid`、`/api/admin/export/json`、`/api/admin/export/csv` 均要求 `Authorization: Bearer <token>`，无令牌或令牌无效返回 401。
- **后台能力**：记录总数与「完成 / 未完成」计数；列表（编号、状态、开始/完成/接收时间、AI标识、一致性、核查状态、`verification`）；单条详情（服务端原始 JSON，含完整核查事件）；单条 JSON 下载；批量 JSON 下载；批量 CSV 下载（稳定列顺序 + UTF-8 BOM）。
- **CSV 语义**：列顺序与 `docs/数据字典.md` 的「CSV 导出列」一致；数组字段以 JSON 字符串写入；缺失值语义与数据字典一致；嵌套原始事件不丢失（见下方）。

## 五、数据完整性与字段

- `verify.count` = 打开过的**不同**材料数；`verify.order` = 不同材料的**首次打开顺序**；`verify.events` 保留重复打开等原始交互。
- `dwell` / `time` 仅作日志，未完成计时不会被误记为零（缺失则为 `null`）。
- `verify_status` 与 `verification` 的派生规则：以 `deriveVerifyStatus` 为准——`not_reached / opened / declined / skipped`；**主 DV `verification=1` 仅当「至少打开 1 份」**，其余为 0。
- **未完成 / 未到达核查步骤 / 技术异常**的记录：`status` 为 `in_progress` 或 `verify_status` 为 `not_reached`，在后台与 CSV 中**明确区分**，不会被静默编码为正常的 `verification=0`。
- 服务端 `raw_json` 原样保存前端提交，导出 JSON 直接回放，包含 `verify.events` 等完整原始数据；CSV 无法表达的嵌套数据可通过配套 JSON 获取。

## 六、需研究者手动完成的事（部署前不会生效）

1. 创建并绑定 D1（绑定名 `DB`）。
2. 执行 `deploy/schema.sql` 建表。
3. 设置 `ADMIN_PASSWORD`、`JWT_SECRET`（Secret）。可选 `ALLOWED_ORIGIN`。
4. 在 `index.html` 填写 `EXP_CONFIG.DATA_ENDPOINT`（提交端点）。
5. 选方案 A 或 B 部署，并访问 `/admin` 验证登录与导出。
